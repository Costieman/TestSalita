# Salita Quest 5.5.8 — Sharing Foundation

## Purpose

This stability release establishes one achievement-sharing owner before the Avatar Case, persistent navigation and Developer Mode are added.

## Root cause repaired

The browser previously loaded both the main achievement-sharing runtime and a later canonical-avatar bridge. The bridge installed a capture-phase click handler, stopped event propagation and replaced `window.SalitaQuestAchievementSharing`. Badge, Badge Chest and level actions could therefore be intercepted by a second controller after the intended controller had already loaded.

The avatar bridge is now compatibility-only:

- it does not replace the shared achievement controller;
- it does not own share clicks;
- it delegates legacy calls to the shared controller;
- it may add the owned-avatar share button to dynamically rendered collection cards;
- locked avatars remain unshareable.

## Unified sharing controller

`achievement-sharing-v4.js` is the single owner for:

- individual earned badges;
- the six-slot Badge Chest;
- individual owned avatars;
- newly unlocked avatars;
- level-up milestones;
- the learner's current level from Progress.

The controller creates both:

- a 1080 × 1080 square image;
- a 1200 × 630 Open Graph image.

Every share type uses the same modal, platform hand-off, native device share, download and copy-link behavior.

## Failure behavior

Hosted preview creation is optional rather than a single point of failure.

When the Cloud Run service or its storage bucket is unavailable:

- the generated square card remains available;
- native device sharing remains available where supported;
- the learner can download the card;
- Facebook, LinkedIn, X and WhatsApp can still open with the Salita Quest app link;
- an explicit status message replaces silent failure.

## Hosted service contract

The Cloud Run service recognizes:

- `badge`
- `badge_chest`
- `avatar`
- `avatar_case`
- `level_up`

`avatar_case` is reserved now for the planned four-avatar showcase so that feature can use the same service without introducing another backend contract.

The health response reports the service version, bucket readiness and supported types. Browser code treats `bucketConfigured: false` as hosted-preview unavailability and preserves local fallbacks.

Service code changes require a Cloud Run redeployment after merge. Repository merge alone does not update the running service.

## Level and avatar integration

Level sharing listens to production progression events and the popup governor. It does not infer level changes by watching celebration markup.

Avatar sharing uses the canonical 48-avatar catalogue and direct canonical PNG paths. Share actions are available from an owned avatar's details and from a newly unlocked avatar celebration.

## Offline update boundary

The PWA cache advances from:

```text
salita-quest-v5-5-7-complete-bisaya-audio-r49
```

to:

```text
salita-quest-v5-5-8-sharing-foundation-r50
```

This causes installed copies to receive the repaired controller and compatibility shim without deleting learner local storage.

## Learner-state safety

This chunk does not change:

- stable course item IDs;
- mastery, due dates or review history;
- XP, coins, streaks or Daily Keys;
- badge ownership;
- avatar ownership, shards or equipped avatar;
- Badge Chest selection;
- profile storage keys;
- JSON backup/import or transfer codes.

## Automated acceptance

The branch must pass:

- Validate Bisaya edition;
- Validate Avatar Progression 5.5;
- semantic sharing-controller checks;
- hosted-service type and metadata checks;
- duplicate-owner prevention checks;
- service-worker cache checks;
- existing placement, progression, audio, badge and avatar regressions.

## Manual acceptance before calling the live feature stable

Test in both Tagalog and Bisaya:

1. Share an individual earned badge.
2. Share a populated Badge Chest.
3. Open an owned avatar and share it.
4. Trigger a new-avatar unlock and share it from the celebration.
5. Share the current level from Progress.
6. Trigger a genuine level-up and share it after the governed celebration.
7. Confirm locked badges and locked avatars cannot be shared.
8. Confirm square-card download works.
9. Confirm native device sharing works on a supported mobile browser.
10. Confirm Facebook, LinkedIn, X and WhatsApp hand-offs open.
11. Confirm hosted preview creation works after the Cloud Run service is redeployed.
12. Simulate hosted-service unavailability and confirm download/device/local-link fallbacks remain usable.
13. Update an installed PWA and confirm learner progress remains intact.

The automated gate can establish code consistency, but the live feature is not considered fully verified until these browser, device and deployed-service checks are completed.
